# Bifrost as a framework: one plugin, two harnesses

Date: 2026-10-22. Status: approved in chat ("приступай"), implementation in progress.

## Intent

Today `@gidragir/bifrost` is a bag of helpers. Plugins do not use it on the Claude side at all: every
`register.tsx` hand-rolls atoms, `$.fs` wrappers, `.catch` guards and command registration, and every
`ui.tsx` copies the same card/truncate/master-detail code. The Antigravity side is a second, unrelated
app (a 578-line `index.html` plus a hand-written `server.mjs`).

The goal is a React-like developer experience:

- state is declared once and used like a variable (`useAtom`, `useState`), never `read($, atom)`;
- a component library (`Card`, `List`, `MasterDetail`, `SearchInput`, `Toolbar`, ...) that takes data
  and renders correctly, enforcing host rules (no `Box` inside `Button`, `Input` availability, the
  90-column split) by itself;
- **one UI description renders in both harnesses**: the Claude Code TUI and the Antigravity (agy)
  auxiliary-pane webview;
- the author writes `src/plugin.tsx` (+ pure logic); manifests, the Claude hooks module, the agy server,
  HTML, CSS and client JS are generated by `bifrost build`.

"sidecar" is renamed to **agy** everywhere we own the name. Names that are Antigravity's contract stay
(`sidecar.json`, `window.sidecar`, `ANTIGRAVITY_SIDECAR_*`, `sidecars/<id>/` inside the built plugin).

## Non-goals

- Antigravity slash commands / hooks (agy has no runtime event model equivalent to Claude's hooks yet).
- Component-instance-local state (state is keyed by name, which is what survives hot reload in Claude).
- Pixel parity between TUI and web; parity of behaviour and structure is the target.

## Hard constraints discovered by spikes (Claude Code 2.1.306)

The engine statically scans the hooks module and refuses to load it unless:

1. `on('<event>', ...)` uses a string literal event name (matcher values may be variables);
2. `atom({ plugin: '<lit>', key: '<lit>' }, ...)` refs are literals, and `read`/`update` receive such an
   atom written in a `const` of the file;
3. `$` is only spelled `$.noun.verb(...)` or passed to a top-level named / imported function;
4. `register` is exported as a const function, and `on` is passed only to a top-level / imported function;
5. state keys are declared in the manifest's `types` contract (`interface PluginState`).

Consequence: the Claude entry must be **code-generated** per plugin. `bifrost build` evaluates the
plugin in Node to learn its atoms and panes, then emits a virtual module with literal atoms and
`switch`-based `readCell($, key)` / `writeCell($, key, fn)`, plus `types/state.d.ts`.

## Architecture

```
plugins/<mod>/src/plugin.tsx   definePlugin({ name, version, panes, commands, claude, config })
        │  JSX via @gidragir/bifrost/jsx-runtime → neutral VNode tree
        ▼
@gidragir/bifrost (core)       atom/useAtom/useHost/useViewport, primitives (Box, Text, Button, Input,
                               Select, Markdown, Code, Link), components, Host (ctx) interface
        ├─ /claude             install(on, options, plugin): hooks, ctx over $, VNode → engine elements
        ├─ /agy                runAgy(plugin): node:http server, VNode → HTML (+ handler ids),
        │                      client runtime, SSE live updates, effects (toast, prompt, focus)
        ├─ /testing            mount(plugin, pane, { harness }) → find/press/input/html, runCommand
        └─ /cli                bifrost build|dev: codegen + esbuild → plugins/<mod>/dist (installable)
```

- **State**: `atom(key, initial)` declared at module level; `useAtom(a)` → `[value, set]`;
  `useState(key, initial)` is sugar (key must be a string literal so the build can see it).
  Claude: engine atoms (session state, survive hot reload). agy: in-process store with SSE push.
- **Host (ctx)**: one interface for both harnesses — `get/set`, `fs`, `cwd()`, `config(key)`,
  `selection()`, `prompt.append/replace/read/submit`, `toast`, `pane.open/close/focus`, `scrollTo`.
  Every method is guarded (never throws into the host). Missing capabilities degrade quietly.
- **Rendering**: components are plain functions evaluated eagerly; hooks are keyed by name, not by
  call order. The renderer preloads the atoms a pane used last time, renders, and re-renders once if
  a new atom showed up.
- **Claude-only events**: `claude.promptSubmit`, `claude.turnComplete`, `claude.sessionStart`,
  `claude.configChange`. For anything else, an optional raw `src/claude.ts` hooks module is bundled
  next to the generated one.
- **Output**: `plugins/<mod>/dist/` is a complete plugin for both harnesses (`.claude-plugin/`,
  `hooks/`, `types/`, `plugin.json`, `skills/`, `rules/`, `sidecars/<mod>/`). Dev links and release
  branches point at it. Source folders contain no generated files.

## Calls made by the builder (Claude), open to review

- Metadata lives in `definePlugin` (single source); `author/license/repository` default from the root
  `package.json`.
- Engine tests live in `test/engine/*.ts` and are copied to `dist/tests/*.test.ts` for
  `claude plugin test`; Bun runs `*.test.ts(x)` only.
- `packages/ui`, `packages/react`, `packages/claude-code` shims and vendored web assets are removed.
- `marketplace.json` points at release branches; `.agents/plugins.json` points at `dist/` folders.
- The domain-specific artifact-ID badge highlighting in markdown SSR is dropped from the framework.
